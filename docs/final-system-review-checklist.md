# Final system review — pre-implementation checklist

Review date: November 9, 2026 (Asia/Manila).

Scope: current MERN working copy, registered frontend routes, page/component actions, backend routes, relevant models/controllers, financial and audit safeguards, report flows, shared dialogs and responsive styles. This is a source review with a fresh unit test/build check. It is not a completed live Windows/LAN, physical-print, mobile or multi-user acceptance test. No office database was accessed.

No new application changes were implemented during this review. The earlier tested CommissionVouchers centered-error/validation/success fix was already in the working copy during inspection. The user subsequently authorized publishing that tested fix alongside this checklist; checklist recommendations remain unimplemented at publication. All existing work was preserved. No commit, push, merge or deployment was performed during the inspection itself.

Priority: P0 = release blocker; P1 = essential completion/reliability; P2 = polish or optional enhancement. A recommendation is not a claim that the entire module is missing.

## Release blockers / first implementation group

- [ ] **P0: Protect the final active administrator.** `server/src/controllers/userController.js` prevents self-deactivation but permits changing the current administrator's role without checking whether another active administrator remains. Add a concurrency-safe final-administrator guard covering role changes and deactivation, with clear UI feedback and audit details. Test concurrent changes as well as one remaining administrator.
- [ ] **P0: Make blocking feedback visible across the system.** Standardize action success/errors/warnings/confirmations through a shared screen-centered dialog/notification host rendered at document-body level. Existing `CenterPopup.jsx` uses an inline z-index of 2000, while the field-help tooltip uses 3100; many pages use inline alerts only. Nested stacking contexts and inconsistent modal values prevent a global visibility guarantee. Use a coordinated modal stack, not merely a bigger number. Preserve inline validation as additional guidance. Blocking dialogs must cover underlying content, dismiss background tooltips, trap focus in the actual topmost dialog, restore focus, and avoid accidental Enter confirmation of destructive actions.
- [ ] **P0 sign-off gate: Prove expense correction and void workflows.** There is no general expense update/void route or UI. `Expense.status` supports VOIDED, but finance routes expose only creation and classification. Add administrator-authorized, reasoned, version-checked, idempotent correction/void with immutable original history; verify collection/cash/report/payout-link effects before operational sign-off. Never delete a posted expense.

## Additional confirmed reliability findings

1. **Financial previews versus notification reads:** `server/src/controllers/notificationController.js` increments account `__v` when marking notifications read. Financial previews/reconciliation bind to that same version. Therefore a nonfinancial read can invalidate a preview. Use a financial revision/fingerprint independent of read flags, while still rejecting real financial edits. Include scheduled monitoring updates and concurrent-user tests.
2. **Cash history truncation:** `listCashEntries` uses `.limit(200)` with no pagination. This does not prove report totals are truncated (reports use separate queries), but older ledger entries are inaccessible through that listing.
3. **Notification history truncation:** `notificationData` returns `rows.slice(0,100)` but computes unread from the whole visible history. Older unread records can be counted without being individually visible. Keep important history and provide paging rather than deleting it to fix the badge.
4. **Large-book backup risk:** `createRestorePoint` materializes an entire collection with `toArray()`, creates an EJSON buffer, reads/parses it again, and checks the 100MB limit only after allocation. Recalculation invokes it during a transaction. Load-test bounded/streamed backup and transaction duration; preserve a verified consistent restore point and atomic financial changes. No measured office-data memory failure is claimed by this static review.
5. **Large-book read/export risk:** several account/report/notification flows load all matching accounts or records. Add server pagination/projections and bounded export processing while retaining totals for the entire scope. Do not calculate totals from just a displayed page.
6. **Global feedback/keyboard mismatch:** popup focus logic chooses the last modal in DOM order, not a coordinated topmost visible dialog. A higher-z-index alert inserted earlier than an inner dialog can lose focus priority. Resolve through one managed portal/stack and test real nested workflows.
7. **Role-aware UI:** backend authorization exists, but some entry pages such as Projects and Expenses render mutation controls without checking the viewer's role. Hide or disable them with explanations; never remove server authorization.
8. **Error recovery:** App uses Suspense for lazy loading but has no application error boundary. Add a useful recovery page/retry and safe API/auth error handling; avoid exposing raw server internals in production responses.

## Delete/archive/restore rules to implement consistently

- Posted payments, penalties, commissions, vouchers and expenses: void/correct/reverse with reason/authorization and immutable originals. Archiving must not remove their financial effect from reports. Never hard-delete them.
- Clients, agents, projects, companies and users with history: deactivate/archive and restore/reactivate, preserving links. Reactivating a client must not silently reinstate a forfeited contract.
- Unsaved entries, nonactivated migration drafts and genuinely unlinked unused setup records: confirmed removal with role checks. Audit persisted removals.
- Lots/phases/blocks: preserve existing available/unlinked/empty-child restrictions and recheck eligibility atomically.
- Activity logs, payout history and activated migration records: read-only history, not ordinary deletion targets.
