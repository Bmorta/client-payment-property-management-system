# Historical Data Migration — implementation and office testing

This update adds Historical Data Migration on `feature/property-inventory`, following commit `4e4a71e`. Publishing the code does not import office data, run seeds, change connection credentials, deploy, or activate historical records.

## Preparation Mode fix

Historical staging no longer requires an official cutoff. With no configuration, or with a blank cutoff, the module shows Preparation Mode. From Dashboard select **Start Migration** or **Open** for a client-property account, then use Manual Encoding or Excel Import. Draft saving/editing, previews, duplicate validation, reconciliation, progress and administrator verification remain available. Dates must still be valid, not future-dated and not before the linked contract.

The Configuration cutoff is optional during preparation. A preparation reconciliation is explicitly provisional and shows its as-of date (today in Asia/Manila); that date is not saved as an official cutoff. Draft/Not Activated labels distinguish these records from live payments. Preparation previews do not write to live accounts, balances, penalties, commissions, forfeiture or cash.

Financial activation remains disabled in the interface and rejected by the backend without an official cutoff. Backup/recovery references, reconciliation, administrator approval, transaction support, receipt ownership and idempotency safeguards remain required. After configuring the first official cutoff, refresh the account, return any preparation verification for correction, recalculate and verify again. Rows after that cutoff must be corrected or excluded; the prior preparation approval cannot authorize posting. Existing configured batch snapshots and completed records are preserved.

The nullable cutoff fields require no data reset or migration script. Existing accounts, financial histories, permissions, import limits and configured-cutoff locking remain unchanged.

Fix validation: 152 backend tests passed, 2 optional integrations skipped in the default run; the expanded replica-set HTTP test and standalone safety path passed separately. DOM checks passed preparation-mode manual/Excel staging, optional cutoff, review and disabled activation. Production build passed with the existing nonfatal bundle-size warning. No office database was accessed.

## Working features

- Separate authenticated Historical Data Migration navigation/page for ADMIN and STAFF; VIEWER access is denied on the backend.
- Account inventory includes Not Started accounts and tracks In Progress, Pending Verification, Verified, Completed and Needs Correction. Completion means successful activation, not upload. Search/filter by client/contract/property/project, phase/block/lot, encoder, status and original encoding dates (Philippine calendar dates). Administrators assign encoders and administrator verifiers.
- Version checks prevent stale edits. Only the assigned encoder or an administrator edits drafts. Immutable internal UUID references identify batches, rows, imported transactions and historical payouts. Submitted/verified batches must be returned for correction before editing.
- Manual original-date encoding for down payments, installments, penalty payments, other documented charges, documented penalty assessments/waivers, commission verification and original commission payouts. Save Draft, Save & Add Another and Save & Next Receipt retain account context. Receipt text preserves zeros and numeric next-receipt increment preserves its width. Date Encoded is generated by the server and kept separately from Original Effective Date.
- Six downloadable `.xlsx` template categories (clients, contracts, payments, down payments, penalties, commissions), workbook preflight, formula/macro/external-link rejection, preview, row validation, selected-row staging and a downloadable CSV error report. Manual and Excel rows share normalization and validation. Repeated file hashes and row fingerprints prevent repeated staging. Correct errors in Excel or edit staged financial drafts before submission.
- Duplicate comparison against staged and live original/corrected receipts. Receipt + issuing series is a hard conflict across accounts; date/amount and transaction references are suspects for the same buyer/account. An administrator can document a distinct transaction for a soft match. The duplicate signature is rechecked, so later matching records invalidate the earlier clearance. A hard receipt conflict must be corrected or excluded, not overridden.
- Reconstructs allocations using the existing original contract schedule and production integer-centavo ledger: typed DP, monthly, penalty and other charges remain separate; partial/advance amounts are persisted without duplicate allocation. Contract/client source templates verify that the selected registered records match source details.
- Reconciliation compares the office principal/penalty balances to reconstructed balances at cutoff, shows the full schedule and commission periods, and distinguishes expected contractual penalties from documented historical charges. Differences are never posted as invented charges or balancing payments.
- Historical penalty assessments/waivers carry their original dates and source references. Automatic assessment cycles on/before the approved cutoff are suppressed for activated migrations. Genuine subsequent cycles use existing contractual rules. Closed historical statuses stop new actionable monitoring and collections without deleting balances/history or releasing lots.
- Commission reconciliation uses the existing completed-installment earning rule. Documented earned totals must match the actual agreement. Each payout retains its original date; releases before buyer funding and over-releases are rejected. Multiple partial releases remain separate. No payout is generated merely from importing a buyer payment. Accounts with no commission agreement must explicitly confirm Not Applicable.
- Submit → administrator verify → explicit administrator activation. Independent administrator approval is required when another active administrator is available; sole-administrator self-review requires an audited exception reason. Both original encoders and financial draft modifiers count in that separation check.
- Activation appends payments/payouts, receipt claims, allocation/penalty/commission snapshots and audit events together with Completed status inside a MongoDB transaction. Concurrent activation, retries and receipt-claim conflicts do not duplicate or partially post financial records. A standalone server refuses activation without writing financial records; drafts and review remain usable.
- An official configured cutoff is locked once staging begins, including protection against a concurrent cutoff change. Preparation can precede the initial official cutoff. Live payment posting/preview rejects dates belonging to historical migration. Historic corrections remain in the original historical date window and use the existing reason/preview/approval/revision workflow.
- Original effective dates determine collection report periods. New Historical / Live / All source filters are available in Payment Transactions and Collection & Cash Summary. Historical rows have a source badge, encoding-date context and export/print source labels. Drafts never enter reports. Historical receipts/payouts are excluded from the live physical cash calculation, which requires an authorized opening balance after the migration cutoff. Noncash classifications remain separate.
- Private account/row evidence: PDF/PNG/JPEG preview, 2 MB maximum, 30 active documents per account; authenticated retrieval, MIME signature checks and no-store/nosniff/sandbox response headers. Unverified evidence can be removed/replaced through audited actions; approved evidence is protected. Uploading evidence does not verify it.
- Migration history preserves original imported cells, row corrections, excluded/deleted drafts, file hashes, staff, reasons and review/activation events. Progress has print/Excel preview; Excel rejects a stale progress snapshot. Uploaded binary/base64 content is excluded from the general activity log.

## Intentional boundaries and remaining acceptance work

- Workbooks are **account-scoped**, up to **500 source rows / 4 MB per client-property account**, not a single workbook spanning many unrelated accounts. The whole workbook hash is staged once; remove already-staged rows from a revised workbook when importing additional rows.
- Missing clients and contracts must be created through the existing Clients/Projects/assignment forms using the original contract date, price, DP and schedule. The Clients and Contracts migration templates are source verification sheets; they do **not** bulk-create new live clients/contracts. Source mismatches block approval. Existing fixed contract price/date protections are not bypassed.
- A verified account is activated individually. There is no cross-account bulk activation or automated production import. Approved rows cannot be reopened or deleted as drafts; financial changes use existing administrator corrections. Adding a missed new receipt after completion needs a separately reviewed supplemental migration procedure, not backdating a new live collection.
- There is no invented balancing adjustment. Unsupported or inconsistent contract/penalty/commission evidence must be reconciled before activation. Documentary penalties can be increased through an assessment or reduced through a waiver, each with a source and reason. The expected-versus-recorded difference remains informational.
- Existing monitoring may already apply to a registered live contract. Creating an original contract through the regular forms remains a live audited operation; do this in staging first. This module does not silently disable monitoring for existing live accounts merely because a draft migration was opened.
- Actual office workbooks/printed records, real backup restoration, operator/device acceptance, printed output and production database topology have **not** been validated. Backup/recovery reference fields are administrator attestations, not an automated backup tool. Do not label a production backup verified without actually testing it.
- Existing large-bundle build warning remains nonfatal. The new page is lazy-loaded and no production dependencies were added.

## Schema changes

New collections:

1. `MigrationBatch`: unique batch/account references, nullable cutoff snapshot during preparation, encoder/verifier, staging rows, file hashes/import sources, reconciliation, approval/activation details and append-only history. One batch per account; compare-and-swap `__v` checks.
2. `MigrationConfig`: singleton OFFICE optional preparation cutoff, staging-start lock, backup and recovery references, version, activation sequence and history.
3. `MigrationDocument`: authenticated evidence bytes, account/batch/optional row relationship, MIME/hash and removal metadata/history.

Extended PropertyAssignment:

- `migration`: approved cutoff, source batch, documented account status, activation time/approver.
- `historicalPenalties`: documented assessments; existing waiver history retains migration source references.
- Payments gain immutable `origin` (`LIVE` default / `HISTORICAL`), migration batch/row references and historical OTHER charge support. Original payments remain append-only; corrections use existing revisions.
- Existing commission payouts store historical origin/batch/row references and original actual release dates in their existing mixed record schema.

No migration script, seed or reset is needed. Existing documents remain valid. New collections/indexes are created by Mongoose as used. No office records were changed during implementation.

## Run locally

From the repository root, start the two usual terminals:

```powershell
npm --prefix server run dev
```

```powershell
npm --prefix client run dev
```

Keep the existing `server/.env` and MongoDB connection. For initial testing, use a separate staging database; do not point a trial migration at the office database. No new dependency install is needed if existing dependencies are already installed. Pull the approved feature/property-inventory update before running these instructions.

## Operator test

1. Log in as administrator and open Historical Data Migration → Configuration.
2. Leave the cutoff blank while planning. Before activation, set the actual historical cutoff (must precede today); once official and staging exists, it is locked. Only enter backup/recovery references for actual completed tests.
3. Register/link a test client and property contract using original dates and terms. For the simple example, use 12 monthly installments of PHP 6,000, no DP, and no commission agreement. Keep this in a staging database.
4. Find the account on the dashboard, Start Migration, assign its encoder and administrator verifier.
5. Encode a PHP 15,000 installment receipt on the first due date. Use a text receipt such as `000001` and its actual issuing series. Save & Next Receipt should retain the account/series and offer `000002`.
6. Confirm the live account/payment list is unchanged. Inspect the draft record and its generated encoding date.
7. Download Payments Excel template, use the selected CTR reference and original dates, upload, inspect errors/duplicates and explicitly stage selected valid rows. Re-upload the identical file: it must not duplicate records.
8. Enter the documented office principal balance (PHP 57,000 for the single-receipt example), penalty balance, checked periods, status, source reference and Not Applicable commission review. Save, then Calculate & Preview Allocations. The first two installments should be fully covered and the third should have PHP 3,000 remaining.
9. Submit as encoder, independently review/verify as administrator, refresh the preview and explicitly activate only after backup/recovery and database prerequisites are met.
10. On a replica set, status becomes Completed and original-date rows appear in the live ledger. On a standalone MongoDB server, activation is rejected and staging remains Verified with no partial posting. Do not switch the production DB topology just to bypass that check.
11. Inspect original-period reports, Today's collections, the source filters, preserved receipt text, commission releases if applicable and the opening-cash safeguard. Historical records encoded today must not become today's new collections.
12. Test an approved correction/void through the existing account payment editor. Confirm revisions and commission recovery warnings remain, rather than deleting prior payouts.

## Automated validation

Default backend suite:

```powershell
npm --prefix server test
```

Dedicated migration HTTP test uses a disposable random database named `cpm_migration_test_<uuid>` and drops only that database afterward. Use an isolated test MongoDB server. It detects standalone mode and verifies refusal to activate; use a test replica set for the complete activation/payout/recovery tests.

```powershell
$env:CPM_MIGRATION_TEST_URI = "mongodb://127.0.0.1:27018/?replicaSet=rsMigrationTest"
npm --prefix server run test:migration
Remove-Item Env:CPM_MIGRATION_TEST_URI
```

Existing integration command remains available with its existing `CPM_TEST_MONGO_URI` setup. Frontend build:

```powershell
npm --prefix client run build
```

Validation results are recorded in the final change summary after the checks finish. The new unit suite covers original date/centavo/series validation, partial/advance allocation, documented penalties/waivers, original-period reporting, live-cash protection, closed statuses, OTHER charges, DP separation, immutable completion and workbook preflight. The isolated HTTP suite covers the real API/database approval and transaction paths, concurrent activation, exact import retry, receipt conflict rollback/retry, original payout dates, and correction-related commission recovery.
